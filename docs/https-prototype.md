# StampS3 HTTPS 原型与实机验证

该原型用于判断当前 MicroPython/W5500 是否能直接提供小规模 HTTPS 管理服务，
不是正式 HTTPS 部署，也不启用真实风扇控制或写配置接口。
实际结果见 [2026-10-12 实机测试记录](https-test-2026-10-12.md)，四路并发已出现内存不足。

## 工具与边界

- `tools/https_probe.py`：电脑端编译、生成临时证书、串口部署、负载测试和恢复。
- `tools/https_probe_device.py`：独立设备端测试服务；复用项目模拟采样、Microdot、页面和状态接口。
- 电脑需安装 `mpremote`、`mpy-cross`，并可运行 OpenSSL；不需要安装全局受信任 CA。
- 测试将暂时中断设备当前应用，向唯一 `/https_probe_<随机值>` 目录上传文件，不覆盖业务槽。
- 要求设备没有待试运行 OTA 候选。执行前后比较原有文件 SHA-256 及 OTA 状态，结束后复位恢复业务。
- 设备 RTC 设为当前 UTC，以进行真实证书验证；不刷写底层固件、不安装升级、不修改网络配置。
- 临时 CA、私钥、原始日志和结果存放在被 Git 忽略的 `backups/https-probe-*`，不提交或公开。
  设备只接收服务器私钥和公开 CA 证书，CA 私钥留在电脑；测试结束删除设备临时目录。

示例（串口和 IP 必须替换为已确认设备的值）：

```sh
python tools/https_probe.py --port /dev/cu.usbmodem2101 --device-ip 192.168.1.63 --soak-seconds 180 --max-connections 2
```

运行工具需要 USB 串口和局域网访问权限。电脑同时临时提供一个由测试 CA 签名的 HTTPS 下载源，
用于测试设备“HTTPS 服务端＋HTTPS 客户端”的资源重叠，完成后关闭监听。

## 实现选择

HTTP 对照端口为 8080，HTTPS 为 8443；所有路由都需本次运行随机生成的 Bearer Token。
该 Token 仅控制临时测试端点，HTTP 基线会明文传输它，不是生产凭据，也不接入正式写操作。
默认并发连接上限为 2，单连接处理期限 8 秒；超限关闭连接，不无限等待和分配 TLS 对象。
`--max-connections 4` 用于显式探测高并发边界，可能出现内存不足，不是推荐的生产设置。
`--profile followup` 缩短基线请求数，保留异常连接、模拟维护下载和持续运行，便于针对性复测。

Microdot 2.7.0 的通用 server 启动代码在某些运行时不支持 ssl 参数时会重试明文启动。
原型避开该降级路径：通过 asyncio 接受连接后，明确使用服务端 SSLContext 包装非阻塞 socket，
成功后才交给 Microdot 解析 HTTP。TLS 失败直接关闭，不能作为普通 HTTP 继续处理。
适配依赖 MicroPython 1.29 的 Stream.s 内部结构，正式集成前需固定版本、评审和回归验证。

保留 60 秒模拟采样、1 秒健康监督与 30 秒硬件看门狗。原型的 TLS 适配本身不依赖浏览器关闭校验。
证书使用临时私有 CA、ECDSA P-256 密钥和设备 IP SAN；电脑的 SSLContext 显式信任该 CA，
并验证设备 IP。证书有效期 2 天，不作为长期设备身份。

## 测试矩阵

1. 验证正常证书连接、未知 CA 拒绝、错误设备身份拒绝、未授权 HTTP 请求返回 401。
2. 比较 HTTP 的 1/2/4 路并发与 HTTPS 的 1/2/4 路并发，每次请求均新建连接。
3. 两路并发请求现有 HTML、CSS、JS、字体和 SVG，覆盖首次加载页面的资源路径。
4. TCP 连接后不发 ClientHello，同时发送正常请求；再测试明文误发到 TLS 端口和中途断开。
5. 维护模式模拟：暂停采样，从电脑 HTTPS 下载 512 KiB 到临时文件、分块写 Flash；
   同时通过设备 HTTPS 查询进度，下载结束删除临时文件并立即恢复采样。
6. 默认持续 180 秒的双客户端查询，每轮间隔 2 秒，检查采样序号增长及内存恢复。

下载测试不修改候选槽、NVS 或启动指针，也不测试真实 GitHub 证书链、完整发布清单、
多文件校验/提交或断电回退；它仅覆盖双向 TLS 和临时文件写盘的关键资源重叠。
采样/风扇全为模拟，不能据此认定真实风扇在复位期间的输出已验证。

## 指标与解释

电脑记录 TCP 建连时间、TLS 握手时间、完整响应耗时、TLS 版本/密码套件、状态码及错误。
分阶段汇总成功率、中位数、P95、最大值，不把证书错误或超时算作成功请求。
每条连接都新建 socket，结果不能等同于采用连接复用后的延迟和吞吐。

设备每 100ms 尝试采集 Python 堆，约每秒采集 ESP-IDF HEAP_DATA 空闲量和最大连续块，
另记录最大事件循环延迟、监督间隔、活动连接数、采样序号和采样健康。
这些内存最小值是**离散采样得到的最低空闲值**，不是每次原生分配的精确峰值；同步阻塞阶段可能漏采。
GC 前后的数值也不同，结果中的 heap_free 在阶段末请求 GC 后采集，不能用它替代阶段最低值。
ESP-IDF 与 Python 堆有分配关系，不把两者的空闲字节相加当作总可用内存。

探测器本身的 JSON、监控和双监听器也占用内存，测量值不是最终优化后的生产极限。
若 HTTP 基线和 ping 已较慢，HTTPS 的绝对响应时间包含网络/W5500 路径开销，不能全部归因于 TLS。
短时通过也不代表抗任意拒绝服务攻击；仍需入口隔离、认证、限流和更长时间稳定性测试。

## 结果文件

每次运行生成 `results.json`、各阶段逐请求 JSON、`serial.log`、前后文件/OTA 状态清单和恢复后的 HTTP 状态。
设备复位会重新枚举原生 USB，工具通过原应用的版本及非过期 HTTP 状态验证恢复，不依赖旧串口描述符。
进入串口调试模式最多尝试四次，每次失败关闭并重新打开描述符，不自动刷机或擦除 Flash。
模拟下载有 180 秒整体期限，每次 I/O 最多等待 10 秒；监督器另设 200 秒维护期限，硬件看门狗仍为 30 秒。
最终是否通过需同时检查证书拒绝行为、负载失败数、维护下载结果、采样/看门狗及恢复确认。
若测试中断，先检查串口与原应用是否已恢复；不要直接重复刷机或擦除 Flash。

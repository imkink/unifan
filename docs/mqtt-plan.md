# MQTT 发布方案（讨论稿）

日期：2026-10-11。本文保留原始完整规划。
2026-10-12 已实现并部署首版发布、连接管理、TLS、NVS 配置和 REST 配置接口；
事件、统一故障码、HA Discovery 和历史仍未实现。实际范围、IPv4/TLS 限制及运维以
[当前服务说明](services.md) 为准，下文“尚未实现”反映规划时的状态。
默认面向通用 Broker / Node-RED；Home Assistant 自动发现作为可选适配层。

## 1. 项目现状与目标

- StampS3 + 官方 MicroPython，经 W5500 联网；沿用现有 `asyncio` 事件循环。
- `TelemetryService` 启动时立即采样一次，之后每 1 分钟生成一个完整快照，包含温湿度、6 路转速和风扇所属 PWM 组。
- 风扇 1～4 属于组 1，5～6 属于组 2；只有两组 PWM 输出，六路 RPM 独立。
- 当前温湿度、PWM、RPM 都是模拟数据，真实驱动、控制策略、告警判断尚未实现。
- 采样过期阈值为 90 秒，本地监督每秒检查一次，硬件看门狗为 30 秒；后两者不随采样降频。
- 全局周期已确定：采样每 1 分钟，常规发布与历史记录每 10 分钟；历史保留 7 天。
- Web 已发布 `/api/status`；MQTT 应读取相同的内存服务，不调用 HTTP 自取数据，也不重新采样。
- 原始需求要求 MQTT 发布温湿度、6 路 RPM 和系统状态码；专门的 MQTT 需求文档尚未细化。

首版范围：配置与连接管理、当前状态发布、在线状态、设备信息、可观测的错误与重连。
不在本次发布模块中加入远程调速、远程配置或 OTA 命令订阅。未来需要时另行定义命令协议。

## 2. 模块及接入点

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| `mqtt_config.py` | 默认值、配置校验、独立 NVS 配置读写 | 用户配置不写回 `app_config.py`，不随 A/B 更新丢失 |
| `mqtt_transport.py` | 封装经过验证的 MQTT 客户端；连接、TLS、PING、QoS 1、遗嘱 | 不读取传感器、不解释故障、不控制风扇 |
| `mqtt_service.py` | 单一后台任务；连接状态机、快照调度、去重、重连、有界缓存 | 普通 Broker 故障留在模块内处理，不能阻塞本地控制 |
| `mqtt_payload.py` | 由共享快照生成版本化 JSON、topic 和设备信息 | 纯数据转换，方便用主机测试固定协议 |
| 共享设备信息与健康状态 | 统一 ID、版本、时间有效性、当前故障、状态码映射 | 应供 Web / 串口 / MQTT 共用，不能成为 MQTT 私有判断 |

`app.py` 创建并管理 MQTT 服务任务；`webapp.py` 可读取其 `status()`，显示连接阶段、
最近一次 PUBACK、重连次数、脱敏错误和丢弃计数。MQTT 服务不能依赖 Web 层的 payload builder。
把当前 `webapp._device_id()` 的能力移入共享模块，避免两种接口生成不同设备身份。

MQTT 客户端优先选择兼容该 MicroPython/W5500 环境的异步实现，第一阶段验证后锁定版本。
协议基线为 MQTT 3.1.1、QoS 0/1，不依赖 MQTT 5。依赖应评估放入 A/B 业务目录随版本更新；
若选择固定 `/lib` 部署，必须明确其独立安装步骤，现有 OTA 不更新公共依赖。

## 3. 身份与 topic

沿用当前 API 的完整 `machine.unique_id()` 大写十六进制值作为 `device_id`。
旧需求中的 8 位随机 UUID 暂不引入，避免和现有设备 ID 形成两套身份。
不得用 IP、设备名称或未确认唯一性的短 ID 作为唯一键；取不到有效 ID 时停用 MQTT 并报告错误，
不能把所有设备都发布到 `UNKNOWN`。

- 真实数据基础路径：`unifan/<device_id>`。
- 模拟数据基础路径：`unifan/sim/<device_id>`，同时在 payload 保留来源标志。
- Client ID：`unifan-<device_id>`；桌面模拟器使用单独后缀，不能挤掉实机连接。
- 本文表格中的 `base` 表示对应基础路径。Topic 前缀可配置，但禁止通配符及不受控空路径。

| Topic | 内容 | QoS | Retain | 发布时机 |
| --- | --- | --- | --- | --- |
| `base/availability` | 纯文本 `online` / `offline` | 1 | 是 | 连接初始化完成、主动退出、Broker 遗嘱 |
| `base/state` | 完整运行状态 JSON | 1 | 是 | 首次连接/重连、每 10 分钟、故障转换 |
| `base/info` | 静态设备信息 JSON | 1 | 是 | 每次连接及信息变化 |
| `base/event` | 故障发生/恢复等离散事件 JSON | 1 | 否 | 事件真正发生时；随共享故障服务接入 |
| `base/sys_code` | 十进制整数文本，如 `0`、`-101` | 1 | 是 | 可选兼容输出；统一状态码完成后启用 |

首版必需前三个 topic。状态码正式启用后在 `state` 中包含相同数值；独立 `sys_code`
仅服务需要纯数字的订阅者。`event` 是状态变化通知，不是完整串口日志，也不是可靠审计日志。
默认不逐风扇拆出大量标量 topic；JSON 已能表达同一次采样，Node-RED 和 HA 都可按字段取值。

切换前缀或模拟/真实模式属于 topic 迁移：尽可能先在旧路径发布 `offline`，清理旧 retained
消息后再连接新路径。旧 Broker 不可达时在本地记录待清理项，并明确提示旧路径可能仍有缓存，
不能声称已完成远端清理。HA 配置若已发布也需同步删除。

## 4. 发布内容

`state` 字段契约如下；新字段是拟新增能力，不代表当前采样层已有这些信息。

| 字段 | 内容与语义 |
| --- | --- |
| `schema` | 消息结构主版本，首版为 `1`；破坏兼容时递增 |
| `device_id`、`boot_id` | 固定设备 ID；每次启动生成的运行 ID，区分重启前后序号 |
| `publish_seq`、`sample_seq` | 本次启动内逻辑消息序号、采样序号；重发同一消息不增加 `publish_seq` |
| `sampled_at`、`published_at` | UTC ISO 8601；时钟未确认同步时为 `null` |
| `time_synced`、`uptime_ms`、`sample_age_ms` | 时间是否可信、单调累计运行时间、发布时样本年龄 |
| `source`、`simulated`、`stale` | 沿用采样来源和过期语义；模拟数据永远明确标记 |
| `hardware_ready`、`control_policy_ready` | 分别表示真实硬件与控制策略就绪，不由 MQTT 连接成功推导 |
| `environment` | `temperature_c`、`humidity_percent`；另含 `quality` 与必要错误标识 |
| `groups` | 组 1/2 的 `id`、`pwm_percent`、`mode`；策略未实现时模式为 `unconfigured` |
| `fans` | 固定 ID 1～6，每项含 `id`、`group`、`rpm`、`quality`、`status` |
| `health`、`sys_code` | 汇总健康状态及兼容数字码；未完成统一映射时码为 `null` |
| `active_faults` | 当前故障集合，包含稳定故障键、严重度、对象；尚未实现判断时为 `null` |
| `network` | 接口、当前 IP、网络阶段；不默认发布掩码、网关和 DNS |

MQTT 中按组发布 PWM，避免让订阅者误解为六路可独立调速。Web 现有结构可保持兼容，
由 MQTT 序列化层从同一个完整快照构造 `groups`。

数值规则：温度保留 1 位小数、湿度保留 1 位小数、PWM 百分比、RPM 整数；单位写在字段名中。
`quality` 可为 `valid / simulated / invalid / stale / unknown`，模拟来源另由 `source` 永久保留。
无效或过期的当前数值使用 `null`，不能填 `0`，也不能把旧读数当作新读数继续发布。
若未来需要显示最后一次有效值，应使用独立的 `last_good` 字段及其时间，不能混在当前值里。

模拟风扇的 `status` 为 `unknown`，`quality` 为 `simulated`；不得因为演示 RPM 非零就声明
真实风扇正常。真实 RPM 为 0 也不自动等于“未接风扇”：停转、测速失败和物理未接须由硬件策略判断。

`info` 包含 `schema`、`device_id`、产品名称、主控型号、固件版本、协议版本、
6 路风扇/2 组 PWM 的能力说明及来源模式。内存余量、重连统计等诊断数据优先留在 Web 状态，
确有监控需求时再增设低频 diagnostics；不发布密码、证书私钥或完整配置。

## 5. 发布调度与故障判断

| 场景 | 建议行为 |
| --- | --- |
| 正常运行 | 每 1 分钟采样，每 10 分钟发布一次最新完整 `state`，即使数值未变 |
| 普通数值变化 | 只更新内存，合并到下一次 10 分钟发布，不再按温湿度/PWM/RPM 变化阈值提前发布 |
| 历史记录 | 每 10 分钟保存一次最新快照及其采样时间/质量，保留 7 天；不逐条保存全部分钟样本 |
| 故障发生/恢复 | 检测到转换时立即安排当前 `state` 和对应事件，不等待 10 分钟周期；同一故障只在转换时产生事件 |
| 首次连接/重连 | 无论数值是否变化都发布 `info`、最新 `state`，获 ACK 后发布 `online` |
| 数据过期 | 采用 ≥90 秒边界；有机会发送时发布 stale 状态，不能等待 MQTT 后再执行本地保护/重启 |

发布和记录使用各自的单调计时期限，每 600 秒处理一次最新快照；Broker 断线不影响本地记录。
两者同一时刻到期时优先使用该轮已完成的新采样；没有更新则保留真实样本年龄，不伪造采样时间。
首个周期记录在启动后 10 分钟发生；事件发布不重置周期期限，与到期发布重合时合并为一条 state。
重连即时发布后重新计算下一次周期发布期限，历史记录期限不受重连影响。
记录时无有效数据则保存空值及质量标记，不用旧值填补，也不在恢复后伪造缺失期间的样本。
7 天正常周期记录共 1008 条；分钟采样留在内存，10 分钟记录默认取最新值，不自动计算平均值。

故障判断由共享状态/控制服务负责，MQTT 只传递结果。每分钟采样不能证明温度连续 5 秒或
10 秒越限，取消原来的秒级持续时间建议。高温阈值、恢复迟滞和连续异常样本数由后续
控制策略确定；事件即时发布指“检测到后立即安排”，不是承诺秒级发现温度变化。
风扇失速的启动宽限期、最低有效转速和连续异常次数必须在真实测速可用后标定。

当前采样读取异常会使任务退出，并由应用监督导致重启；MQTT 不能承诺在这一窗口送出故障消息。
若要求稳定发布传感器单项故障，需要先扩展采样层的单项质量/错误状态与本地故障保护。
这不能只靠 MQTT 层捕获异常完成。

## 6. 状态码与事件

原状态码表同时包含 `100` 初始化风扇、`410` MQTT 就绪这类过程信息，以及负数故障码。
不能把“最后一条日志代码”当作当前健康状态，否则一次连接成功就可能覆盖仍存在的风扇故障。

- `event.code` 表达一次过程事件；同时提供稳定字符串类型与对象，例如 `fan_fault_started` / `fan:3`。
- `state.active_faults` 表达全部当前故障；空数组仅表示故障评估已完成且没有活动故障。
- `state.sys_code` 是故障集合的主故障投影：严重度优先，再按固定模块/对象顺序选择，避免抖动。
- 正式运行且全部必需检查通过、无故障时才给出正常码 `0`。模拟模式使用明确的模拟状态，
  当前没有约定的数字映射，先用 `null`，不自创与既有表冲突的“正常”码。
- 严重度、所有负数码和模拟状态码应统一补入共享状态码表；MQTT、Web、串口使用同一来源。

事件包含 `schema`、`device_id`、`boot_id`、`event_seq`、事件类型、故障键、
发生时间或运行时间、`active` 和必要数据。消费者按 `(device_id, boot_id, event_seq)` 去重。
故障消失只发一次恢复事件，持续故障仍体现在周期 `state` 中。
MQTT 自身断线期间不能实时上报其故障；恢复后可发重连事件及持续时长，实时离线判断依赖遗嘱。

## 7. 连接、可靠性与本地业务隔离

状态机：`disabled → waiting_network → connecting → online → backoff`；
配置错误进入 `config_error` 等待修改，不高频死循环重试。

默认 `keepalive=30s`，连接/ACK 等可取消操作的期限先设 5 秒；重连采用
1、2、4、8、16、32、60 秒上限的指数退避，附加 ±20% 抖动，稳定在线 60 秒后重置。
无可用以太网时只等待网卡恢复，不能循环重建 W5500。认证失败用慢速重试并在 Web 显示明确原因。

采用 `clean_session=true`。当前仅发布，不需要 Broker 保留订阅会话或历史待投递队列。
QoS 1 代表至少一次交给 Broker，不保证所有订阅者完成处理，也不能保证不重复。
逻辑消息使用 `(device_id, boot_id, publish_seq)` 去重；订阅者也应拒绝同一启动中倒退的序号。

遗嘱在 CONNECT 时注册：`base/availability=offline`，QoS 1、retain。
`online` 只说明 MQTT 发布通道已建立且初始信息已送达，不代表硬件正常；模拟设备也可以 online。
异常断电/断网由 Broker 在连接丢失或 keepalive 超时后发布遗嘱，不能保证瞬时变化；
常见超时约为 1.5 倍 keepalive，最终取决于 Broker 检测时机。
主动停用/重启时先尽力发布 retained `offline` 并等待有限时间的 ACK，再正常 DISCONNECT；
若未确认离线消息，关闭异常连接以保留遗嘱机制，不因发送标准 DISCONNECT 而压掉遗嘱。

状态缓存只保留每个主题的最新待发送内容；一个 QoS 1 消息在途时不修改其序号和内容，
后续状态合并到待发送槽。断线重连后生成最新快照，不逐条重放旧遥测。
事件队列建议最多 16 条且总编码大小不超过 8 KiB，单条事件最多 512 字节；
溢出丢弃最旧事件并增加 `dropped_events`，重连先发送当前状态再补有限事件。
不为发布每次写 Flash，不保证断电后保留事件。若未来需要可靠审计，应单独设计持久化队列。
完整 state 先以 4 KiB 为编码上限，并测量序列化、队列和 TLS 对象的实际峰值内存。

本地启动确认不能等待 Broker；MQTT 网络错误不能使风扇控制停摆、停止喂狗或触发 OTA 回退。
预期传输错误在服务内恢复；MQTT 任务意外退出应被本地监督发现，记录错误并有界重启/停用服务，
不能简单加入当前“任何任务退出都重启全机”的核心任务列表。
正常运行时核心采样/控制任务的既有健康检查仍然独立执行。

OTA 采用 [维护模式](ota-maintenance.md)：先置 `paused_for_ota` 抑制重连，尽力发布 offline 后
释放 MQTT socket/TLS 与待发缓冲；暂停期间不保活、不连接、不发布，采样和普通 REST 同时暂停。
OTA 检查结束、失败或安装完成等待重启时，先恢复本地新鲜采样，再恢复原本启用的 MQTT。
重连按既定顺序发布 info/state/online，不能以冻结的旧快照宣布恢复；Broker 不可达不阻碍本地业务恢复。

MicroPython 的 DNS、TLS 握手或第三方客户端内部可能同步阻塞；外层包一层 `async` 或超时
不能保证可中断。选库阶段必须实测失败 DNS、黑洞连接和 TLS 握手期间的采样与 Web 响应。
必要时采用明确 Broker IP 配置或支持非阻塞握手的实现，TLS 仍须验证证书中的服务器身份。
发现无法限制的阻塞则视为该传输方案未通过验收，不能为迁就 MQTT 而放宽采样健康标准。

## 8. 时间、保留消息与配置

发布间隔、重连、数据年龄均用单调计时，不受校时影响；使用 `ticks_diff` 处理计时器回绕。
长期 uptime 需累计差值，不能直接把会回绕的 `ticks_ms()` 当作永久递增时间。
项目尚无自动 NTP；`time_synced` 必须由真实校时状态产生，不能只看年份“像是正确”就置真。

Retain 表示“最后一次状态”，不是“当前仍有效”。消费者同时检查 availability 和新鲜度：
默认 10 分钟发布周期下，连续 30 分钟没有新状态应标记数据不可用，即使 availability 仍为 online。
这与设备本地的 90 秒采样过期阈值不同：订阅者收到的是每 10 分钟更新的快照，不应在收到
90 秒后就把正常的周期发布判为失败。`stale=true` 或 `offline` 到达时立即标记不可用。
有可信 UTC 时按发布周期及允许样本年龄校验时间；时钟未知时，首次收到 retained state 只能展示为未确认历史值，
应等待新的实时发布后再认为有效。`sample_age_ms` 仅表示发送当时的年龄，不能扣除 Broker 留存时间。

配置放在独立 `unifan_mqtt` NVS 命名空间的版本化配置记录中，仅显式保存时写入。
建议字段：启用开关、Broker 主机/端口、TLS 模式与 CA 路径、用户名/密码、topic 前缀、
发布周期（默认 600 秒）；Client ID 自动派生。默认关闭，配置有效后启用；默认端口明文 1883、TLS 8883。
TLS 开启时严格验证证书/服务器身份，时钟无效导致校验失败时保持本地业务、报告问题并重试，
不能退回明文。局域网明文模式应由用户明确选择；NVS 持久化本身不等于凭据加密。

Broker 账号按设备 topic 授权，密码和密钥不进入版本库、发布包、状态接口或日志。
当前 Web 设置按钮禁用，因此首版可通过受控 USB 配置；网页编辑、连接测试与保存应在设置持久化
和鉴权方案完成后接入。变更连接配置应有界关闭旧连接并重新初始化，新配置不反复写 Flash。

## 9. 落地顺序与验收

1. 固定 topic、字段和设备身份；实现最小共享身份/时间元数据与配置存储，保留模拟来源。
2. 验证异步客户端与 W5500，接入 availability / info / state、重连与本地连接状态展示。
3. 完善共享健康/故障语义，再接入 sys_code、告警与事件；不为发布功能提前伪造硬件检测结果。
4. 若接收端是 Home Assistant，增加独立 Discovery 适配层：温湿度、6 个 RPM、2 个 PWM、
   故障/可用性实体；稳定 unique_id、统一 device 分组、模拟设备名称标识、过期判定和配置清理。
   只配置监测实体，不暴露尚不存在的远程风扇控制能力。

验收覆盖：正常/模拟/无效/过期 payload，分钟采样与 10 分钟发布/记录调度，QoS 重复与重连，事件队列溢出，
网线拔插、Broker 停机/重启、错误密码、ACK 超时、断电遗嘱、无效时钟与 TLS 失败、
NVS 配置跨 A/B 更新保留，以及 MQTT 故障下采样/看门狗/Web 仍正常。
重启 Broker 后须重新发布 retained 状态；设备重启须更换 boot_id。
正常 MQTT TLS 与 Web 的并发峰值、OTA 暂停前后的资源释放和恢复峰值需要实机验证，
不能用首次部署的空闲堆采样代替；维护暂停时不得留下 MQTT 自动重连与 OTA TLS 竞争资源。

尚需用户环境信息：接收系统及是否需要 HA Discovery、Broker 地址、认证方式、是否必须 TLS。
这些信息影响集成配置，不阻止通用协议和模块先行确定。1 分钟采样、10 分钟发布/记录已由用户确定；
其他超时、队列大小等仍为建议默认值。

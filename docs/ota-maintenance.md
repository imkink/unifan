# OTA 维护模式方案

日期：2026-10-11。根据“OTA 时先停止采样、MQTT 和 REST”的要求制定；本文件为设计，
当前固件尚未实现维护协调器。关联：[OTA](ota.md)、[MQTT](mqtt-plan.md)、[REST](rest-plan.md)。

## 1. 范围与保留能力

OTA 使用有界维护窗口，主动释放业务连接和临时缓冲，降低 HTTPS 下载与业务并行造成的内存峰值。
检查版本也涉及 HTTPS，按同一流程短暂进入维护；正式安装在用户选定版本后再次进入。
检查结束、安装失败或安装完成但等待手动重启时均恢复业务；点击升级重启时重新进入短暂维护。
不改变既有“下载完成不自动重启、候选启动自检确认、失败回退”的规则。

| 能力 | OTA 维护期间行为 |
| --- | --- |
| 温湿度及风扇状态采样 | 暂停周期任务，不发起新的采样；保留最后快照但明确标记暂停/过期 |
| 温控策略更新 | 停止依据温度计算新目标，维护期间由固定安全输出接管 |
| 风扇 PWM | 继续由硬件维持经验证的安全输出，不能因停采样或销毁任务而停风扇 |
| 测速计数 | 可保留低开销底层计数；不构造业务采样，恢复时重新建立有效测速窗口 |
| MQTT | 尽力发布离线，断开并释放 socket/TLS/在途缓冲；禁止自动重连 |
| 历史记录 | 暂停写入，等待已开始的单条记录完成，避免与 OTA Flash 写入竞争 |
| 普通 REST 与旧 `/api/status` | 暂停业务处理，返回小型 503 maintenance 响应 |
| 正常 Dashboard | 显示轻量维护页面，停止普通状态轮询，不加载字体/图表等资源 |
| OTA 状态与升级重启接口 | 保留鉴权和必要处理，供进度查询与完成后的重启 |
| W5500、事件循环、健康监督与看门狗 | 保留；OTA 依赖网络，不能把这些基础能力一起停掉 |

Web 与 REST 共用 Microdot 监听器，不关闭整个 HTTP 服务。维护页面尽量内联，
`GET /` 返回小型维护页面；普通静态资源和非白名单 API 停止处理，避免继续读大文件。
模块代码不必卸载：取消任务只能释放可回收资源，不保证恢复全部模块导入内存。
释放连接及大缓冲后执行一次受控 GC，再开始 OTA TLS；实际节省量以实机测量为准。

## 2. 维护协调器与进入顺序

由应用层单一 `MaintenanceCoordinator`（拟定模块 `maintenance.py`）管理服务生命周期、
路由门控、维护状态、阶段期限和恢复；复用唯一 Updater，不让各路由独立停止/启动服务。
维护状态先于任务暂停对监督器可见，防止计划内任务退出被旧监督逻辑视为故障。

1. 完成认证、请求参数及候选版本/忙检查，原子取得全局管理操作锁，进入 `quiescing`。
   禁止新的配置写入、历史查询/清理、重复升级及普通重启请求，已在进行的冲突操作返回 409。
2. 等待已接纳的请求、配置提交和单条历史写入有界收尾；停止接纳新的普通请求。
   不能只禁止新请求而放任原有大响应/文件读取继续占用内存。不能及时收尾时中止进入维护并恢复。
3. 通过专用安全输出钩子暂停温控目标更新，并把两组风扇切到经验证的维护输出。
   建议目标是维持充分散热（通常可考虑全速），但 PWM 极性、允许范围和失效状态必须先实机确认；
   不把未经验证的数值 100% 直接当作安全保证。真实模式下安全输出失败则拒绝开始 OTA。
4. 协作暂停采样及历史任务，等待其退出 I2C/采样/写盘临界区；不得从中途取消造成总线或文件半写。
   超时不能靠无条件吞异常继续升级，应恢复原业务或进入明确故障状态。
5. MQTT 先设置 `paused_for_ota` 抑制重连，再尽力发布 retained `offline`（可附维护事件）。
   离线发送设短期限（建议 3 秒）；Broker 不可达不阻塞升级。已确认 offline 时正常断连，
   未确认时异常关闭连接以保留 Broker 遗嘱机制。保留必要的小型事件摘要，释放遥测待发队列及 TLS 引用。
6. 确认任务/连接收尾、维护 HTTP 白名单和监督模式生效，回收临时内存后进入 `ota` 阶段，调用 Updater。

停止与恢复都需可重复调用且不创建重复任务；记录哪些服务原先已启用、哪些已暂停。
MQTT 原本关闭时恢复流程不能自动开启它。任何阶段异常都进入统一清理路径，不能留下自动重连任务。

## 3. 状态与 HTTP 规则

正常流程：`normal → quiescing → ota → resuming → normal`。
安装已提交候选时，恢复后的业务仍运行旧版本，但 OTA 状态为 ready，候选版本等待重启。
升级重启流程：`normal + pending → quiescing → rebooting → 新进程本地自检`。
恢复不成功则进入 `recovery_required`，保持安全输出和最小管理能力，不报告业务已恢复。

维护状态包括 reason、phase、开始时间/运行时间、阶段期限、暂停服务列表、最后错误和恢复进度。
拟在现有 `/api/ota/status` 响应中增加 `maintenance` 对象，保留已有字段兼容。

- 始终保留 `GET /api/ota/status` 和轻量维护页面，以及其必需的最小认证/会话恢复入口。
- `POST /api/ota/reboot` 只在候选已完整提交、没有下载/提交/恢复操作进行时允许；提前调用返回 409。
- 已开始维护时，重复 check/install、普通 system/reboot 和历史清理返回 409；不启动第二个任务。
- 普通 GET/设置接口（包括旧 `/api/status` 和 v1 health）返回 503、`Cache-Control: no-store`、
  `Retry-After: 10`，错误码为 `maintenance`；这表示业务计划内不可用，不代表 HTTP 进程死机。
- OTA 与管理接口仍须认证，写请求仍须权限/Origin/CSRF 校验；维护模式不能成为绕过鉴权的路径。
- 已打开的 Dashboard 收到 maintenance 后切换维护展示，停止每 2 秒的普通轮询，
  改为每 3～5 秒查询 OTA 状态；503 中的重试时间是退避提示，不是完成时间承诺。

现有 OTA check 是同步响应语义，首版可以保留并由应用层协调维护；将来改为后台 202 时需要
明确兼容迁移，不在此方案中悄悄改变旧接口协议。即使浏览器断连，已接受的 install 任务也继续运行，
不能通过刷新页面隐式取消正在提交候选的操作。

## 4. 监督与数据真实性

当前 `app.py` 会对采样任务退出和样本 ≥90 秒过期触发异常，不能直接取消采样而不改监督方式。
维护模式只豁免被协调器明确暂停的服务，原有采样时间/序号不能被刷新成“健康新样本”。
恢复时新鲜样本出现前仍保留 paused/stale，未知故障不能因 maintenance 被清空。

看门狗保持开启，由原本的本地健康监督喂养；OTA 下载器和无条件定时器不能自行喂狗。
维护模式健康条件改为：事件循环与必要网络/管理任务存活、安全输出设置已成功、
协调器阶段合法，当前 OTA/恢复步骤没有超过其期限，操作总时长也未超过整体期限。
网络等待允许暂时没有字节进展，但必须受步骤与整体超时约束，不能因任务对象仍存在就无限喂狗。
现有逐次 I/O 和单文件超时不能替代整个多文件升级的总期限，协调器需补上整体期限。
事件循环阻塞仍由原 30 秒看门狗发现；不能为 OTA 延长或关闭它来掩盖同步阻塞。

新候选启动后必须重新建立正常采样及本地关键服务，再执行既有启动确认；
不能把上一个进程的维护模式或安全输出当作候选已通过自检。
维护标志是本次进程的运行状态，不在 NVS 保存“下次启动仍暂停采样”的开关。
复位/掉电期间的实际 PWM 连续性依赖硬件默认电平和驱动行为，软件维护模式不能单独保证。

## 5. 结束、失败与恢复

检查结束（包括没有新版本）、下载/校验失败、超时，以及成功安装但等待重启时，统一恢复：

1. 确认 OTA 任务真正结束并释放 HTTPS/socket/文件句柄；提交临界区不能并发取消和恢复业务。
2. 重读 OTA 持久状态判断候选是否已提交；异常发生在 NVS 保存附近时不能仅凭请求结果假定未提交，
   不擅自删除已提交候选，也不声称下次一定进入旧版本。
3. 保持维护安全输出，恢复采样并立即获取一轮新数据；重建有效测速窗口，再满足本地正常健康条件。
4. 恢复已实现且验证通过的正常控制策略，再开放普通 REST/Dashboard；如果失败，保持安全输出，
   进入 recovery_required，由既定故障恢复策略处理，不能无条件返回 normal。
5. 恢复历史计时，下一次记录在恢复后 10 分钟，维护期间留下记录空档，不重复写入冻结的旧值或补造样本。
6. 恢复原本启用的 MQTT 自动连接；使用新快照发布 info/state，确认后 online，之后每 10 分钟发布。
   MQTT 连不上不阻止本地采样、控制与 REST 恢复，离线情况按原退避机制处理。

采样恢复后继续每分钟更新。重启及 A/B 回退后的新进程也遵循“先本地自检，再启用外部发布”。
软件异常/下载失败保留当前已确认槽；断电后的候选选择仍以固定启动器的实际持久状态为准。

## 6. 接入与验收

应用层增加维护协调器和模式化监督；采样/历史/MQTT 暴露协作暂停与恢复接口；
REST 使用统一门控；OTA 入口必须都经过协调器，不能有绕过维护的自动检查后台任务。
`before_reboot` 仅覆盖最终重启，不足以代替下载开始前的服务暂停。
当前固定 `/lib/unifan_ota` 不随业务 OTA 更新：若接入需要修改其路由或生命周期钩子，
应明确独立部署/兼容方案，不能假定现有设备会自动获得新钩子。

验收包含：每个暂停步骤失败后的恢复、普通请求排空、Broker 不可达仍能进入维护、维护中无自动重连、
停采样超过 90 秒不会被误重启但真卡死仍触发看门狗、下载超时/哈希错误恢复、提交阶段掉电、
完成后长时间不点击重启仍正常采样、恢复失败不误报正常、重复升级/重启拒绝，以及候选自检回退。
分别测量暂停前/后、TLS 握手峰值、恢复后的内存；重复 OTA 检查/失败恢复不能泄漏任务、连接或缓冲。
真实风扇需实测进入维护、下载、复位、新版本启动及回退全过程的输出行为。

# StampS3 直连 HTTPS 实机测试

测试时间：2026-10-11 深夜至 2026-10-12 凌晨（Asia/Shanghai）。

## 结论范围

当前 StampS3/MicroPython/W5500 **能够提供严格校验证书的 HTTPS 服务**，
但不能把“能握手”理解为“可以不受限制地同时跑完整 Web、MQTT、REST 和 OTA”。
四路 HTTPS 新连接并发已经出现内存不足；两路短时可用，但页面资源阶段余量很小。
正式方案宜先采用单个 HTTPS 服务承载 Web 与 REST、限制连接数，并保留网关反向代理选项。

本次没有实现或压测 MQTT、正式 REST v1、历史记录或真实传感器/风扇驱动。
测试不是生产 HTTPS 上线验收，也不能证明对局域网恶意拒绝服务攻击免疫。

## 实测环境

- StampS3，设备 ID `48CA43B5FC00`，W5500 有线网络，设备 IP `192.168.1.63`。
- MicroPython 1.29.0 `ESP32_GENERIC_S3`，CPU 实测 160 MHz，Mbed TLS 3.6.5。
- Microdot 2.7.0；模拟采样每 60 秒，健康监督每秒，看门狗 30 秒。
- HTTP 对照 8080、HTTPS 8443，均运行在独立临时目录。
- 临时内部 CA、ECDSA P-256 服务端证书、IP SAN；客户端显式加载 CA 并验证身份。
- 协商结果：TLS 1.2，`ECDHE-ECDSA-AES256-GCM-SHA384`。
- 请求每次重新建立 TCP/TLS 连接，未复用 TLS 会话。

安全负向检查：电脑客户端不信任 CA 时拒绝连接，使用错误主机名时拒绝连接，
有效 TLS 连接不带令牌时返回 401；向 HTTPS 端口发送明文 HTTP 没有得到明文 HTTP 响应。
下载客户端启用 `CERT_REQUIRED`、加载临时 CA，并使用下载源 IP 做身份验证。
未关闭证书验证、未把临时 CA 安装到电脑全局信任库。
HTTP 基线使用的测试令牌会明文传输，仅为本次临时端点凭据，不能用于生产鉴权。

## 第一轮：并发边界

本轮最大允许 4 个连接；Python 堆监测周期 20ms，原生堆约 200ms。
所有内存均为采样到的最低空闲字节数，而非准确的分配峰值。

| 阶段 | 成功 / 总数 | 响应 P95 | 握手 P95 | Python 堆最低 | 原生堆最低 | 最大连续块最低 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| HTTP，1 路 | 20 / 20 | 2028.75ms | — | 37008 | 49660 | 31744 |
| HTTP，2 路 | 30 / 30 | 2225.39ms | — | 31952 | 49632 | 31744 |
| HTTP，4 路 | 40 / 40 | 2042.50ms | — | 32384 | 49656 | 31744 |
| HTTPS，1 路 | 20 / 20 | 6024.68ms | 4073.14ms | 31968 | 49652 | 31744 |
| HTTPS，2 路 | 30 / 30 | 6103.19ms | 4108.31ms | 13424 | 24696 | 12800 |
| HTTPS，4 路 | 12 / 40 | 5175.56ms | 3068.56ms | 18832 | 22608 | 9728 |
| HTTPS，页面资源 2 路 | 24 / 24 | 7065.36ms | 4100.59ms | 10336 | 17916 | 7680 |

四路阶段设备记录 28 次 `OSError(12)`（ENOMEM），电脑端出现连接重置。
该阶段较低的成功请求耗时**不是性能更好**，因为大多数请求失败，耗时统计仅包含成功请求。
之后两路页面资源请求成功，说明当时服务可以从压力失败中恢复。
各阶段结束主动 GC 后，Python 空闲堆大致回到 86KB。

两路页面资源阶段，Python 最低只剩约 10.1KiB，原生最大连续块约 7.5KiB；
后续再接入 MQTT TLS、历史序列化和真实驱动，不能假定这些余量足够。
Python 与原生堆存在分配关系，不能把两者的空闲量简单相加。

网络路径也有明显延迟：本轮 ping 5/5 成功，平均约 211ms；HTTP 对照同样慢。
因此不能把 HTTPS 的约 6 秒响应全部归因于加密计算，仍需单独定位网络、驱动与运行时调度。

第一轮维护下载在约 60 秒、248064 字节时触发了测试监督器的维护期限，
**没有完成 512KiB 下载，也没有进入持续运行阶段**。这不是一次成功的 OTA 测试。
随后清理完成，测试前后原有文件与 OTA 状态清单完全相同，原应用 HTTP 状态验证为 0.1.2。
主机工具当时因复位后 USB 重新枚举而抛错，导致该轮 `results.json` 的 `restored` 未更新；
恢复证据来自 `before.json` / `after.json` 相等和独立的原应用状态查询，而非该字段。

## 第二轮：维护与短时稳定性复测

复测限制为最多两个入站连接，将 Python 堆监测改为 100ms、原生堆约每秒，
用于降低探测开销；下载整体期限改为 180 秒，维护监督期限 200 秒，看门狗仍为 30 秒。
串口连接增加有界重试及重新打开描述符，恢复验证改用原应用 HTTP 状态。

| 阶段 | 成功 / 总数 | 响应 P95 | Python 堆最低 | 原生堆最低 | 最大连续块最低 |
| --- | ---: | ---: | ---: | ---: | ---: |
| HTTP，1 路 | 5 / 5 | 2014.54ms | 36208 | 50700 | 31744 |
| HTTPS，1 路 | 5 / 5 | 6043.07ms | 31872 | 50896 | 31744 |
| HTTPS，2 路 | 10 / 10 | 6087.16ms | 16864 | 24176 | 12800 |
| 慢连接存在时的有效请求 | 4 / 4 | 6112.53ms | 32192 | 27096 | 14336 |
| 维护下载期间进度查询 | 24 / 24 | 5563.07ms | 10608 | 19756 | 8192 |
| 三分钟双客户端查询 | 42 / 42 | 6077.50ms | 18880 | 23696 | 9728 |

降低监控频率未明显消除 HTTPS 延迟，不能将问题简单归因于监测开销。
慢连接/异常报文阶段记录的 6 个预期传输错误，分别为 1 个超时与 5 个非 TLS 报文错误，
不等同于正常业务请求失败。未发送 ClientHello 的连接在期限后释放。

维护下载完整收到 **524288 字节（512KiB）**，分块写临时 Flash 文件后删除，
结束状态为 `done`、`maintenance=false`、`sample_healthy=true`，采样恢复。
同时执行的 24 次 HTTPS 进度查询均成功，无传输错误。
本阶段最大事件循环延迟 829ms，最大健康监督间隔 1415ms；
下载结束 GC 后 Python 堆恢复到 83904 字节。
这覆盖了一个出站 TLS 下载与一个入站 TLS 查询的重叠，
**没有覆盖下载同时两个入站连接，更没有验证真实升级安装/回退**。

三分钟双客户端测试完成，42/42 请求成功，传输错误及超限拒绝均为 0；
采样序号从 5 增加到 8，各检查点均健康，设备运行时间连续，没有观察到重启。
周期性主动 GC 后 Python 空闲堆在 82480–83360 字节间变化，阶段末为 83344 字节；
没有观察到这三分钟内持续不回收的下降，但不足以证明长时间无内存泄漏。
最大事件循环延迟 298ms，最大监督间隔 1293ms。

## 清理、恢复与代码验证

复测进程正常退出（退出码 0），最终结果记录：
`original_files_and_ota_unchanged=true`、`restored=true`。
原有文件 SHA-256 与 OTA 状态的前后清单完全相同；本轮设备临时目录及证书私钥已删除。
原应用 HTTP 状态确认版本仍为 **0.1.2**，采样未过期。
没有刷写 MicroPython 固件、替换 A/B 业务槽、提交升级候选或部署正式 HTTPS 服务。
电脑端临时证书与测试日志仍留在忽略的备份目录，可复查；无需恢复原固件镜像。

主机回归测试 **73 项全部通过**，包含新增的统计与串口重连测试；
主机脚本语法检查、设备端 mpy-cross 编译和 `git diff --check` 均通过。

## 后续集成建议

1. Web 与 REST 共用 HTTPS 监听器、认证、连接预算和序列化缓存，不各开一套 TLS 服务。
2. 先按 **1 个入站 TLS 管理连接**规划余量；两路仅是本次短时测试能力，不作为生产保证。
   浏览器页面需相应减少并发资源请求、启用缓存并避免重复轮询堆积；限流前移到 TLS 分配之前。
3. MQTT 使用一个出站长连接，正式接入后必须重跑内存测试；低发布频率不会消除常驻 TLS 开销。
4. OTA 时暂停普通业务，仅保留最小管理/进度入口；下载流式写入，明确大小、超时与失败恢复边界。
5. 定位当前延迟，再验证浏览器实际首屏、证书更新、长时间运行、网络抖动和完整升级回退。
   若产品要求多客户端顺畅访问，优先采用可信网关 HTTPS 反向代理，或评估 ESP-IDF 实现。
   代理到设备的一段也需受控隔离或加密，不能把上游明文链路当作端到端 HTTPS。
